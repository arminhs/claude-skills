# Documentation conventions (aws-ia style)

Distilled from `arminhs/terraform-aws-vpc`. Each item names the file it was observed in so it can be re-checked.

## Layout

| Convention | Observed in |
|------------|-------------|
| `README.md` is generated output only, wrapped in `<!-- BEGIN_TF_DOCS -->` / `<!-- END_TF_DOCS -->`. Never hand-edit it. | `README.md`, `examples/*/README.md` |
| All prose lives in `.header.md` next to the README. terraform-docs prepends it via `header-from`. | `.header.md`, `examples/*/.header.md`, `.terraform-docs.yaml` |
| One `.terraform-docs.yaml` at the module root: markdown formatter, `output.mode: replace`, inputs sorted with required first, anchors and HTML on. Examples are generated by pointing terraform-docs at the example directory with the root config. | `.terraform-docs.yaml` |
| CI regenerates the README with a pinned terraform-docs version and fails on any diff. | `.github/workflows/ci.yml` (`tag: v0.19.0`, `git diff --exit-code README.md`) |
| Pre-commit runs `aws-ia-meta-hook`, which runs fmt, tflint, and terraform-docs. | `.pre-commit-config.yaml` |
| Supplementary docs live in `docs/`: `UPGRADE-GUIDE-<major>.0.md` and topic guides such as `How-to-use-module-outputs.md`. | `docs/` |
| Contributing guide is `contributing.md` at the root, linked from the last header section. | `contributing.md`, `.header.md` |

## Generated README section order

Requirements, Providers, Modules, Resources, Inputs, Outputs. Inputs table columns: Name, Description, Type, Default, Required. This is what terraform-docs emits with `settings.default: true`; do not reorder. Observed in `README.md`, `examples/basic/README.md`.

## Root `.header.md` outline

Observed in `.header.md`.

1. `# <Module title>` (for example `# AWS VPC Module`).
2. One paragraph summary ending with a link to `examples/`.
3. Italic note pointing at the latest upgrade guide: `<i>Note: For information regarding the 4.0 upgrade see our [upgrade guide](docs/UPGRADE-GUIDE-4.0.md).</i>`
4. `## Usage` with one or two sentences and a complete `module "<name>"` block using the registry `source` and a `version = ">= x.y.0"` constraint.
5. Topic sections, one `##` per feature (`## Reserved Subnet Key Names`, `## Updating a VPC with new or removed subnets`, `## Output usage examples`). Every section is anchored by a code block.
6. Optional `# Common Errors and their Fixes`: each error is a `##`, the raw error is quoted with `>`, fixes are bullets with snippets.
7. Optional `## Production Recommendation: ...` sections for opinionated guidance.
8. `# Contributing` linking to `contributing.md`.

Heading levels in the reference are inconsistent (some topics use `#`, most use `##`). When writing new headers use `##` for everything below the title.

## Example `.header.md` outline

Observed in `examples/basic/.header.md`, `examples/cloud_wan/.header.md`.

```
# <Module title> - Example: <Example name>

This example builds <one sentence>:

* <Feature>
    * <Detail>
* Routing:
    * <Detail>
```

The title after the dash uses the module's short name (`VPC module - Example: Basic VPC`). Bullets use `*` with four-space indented sub-bullets.

## Code blocks

Observed in `.header.md`.

- Fence Terraform snippets as `hcl`. The reference mixes `hcl` and `terraform`; new content uses `hcl`.
- Fence shell transcripts as `shell` and `terraform console` transcripts as `terraform`.
- Placeholders inside HCL are written as `<>` (for example `transit_gateway_id = <>`).
- Non-obvious option values get an inline comment listing the alternatives: `nat_gateway_configuration = "all_azs" # options: "single_az", "none"`.
- Omitted defaults are shown as a commented line: `# name_prefix = "private"` with a comment saying what omitting it does.

## Variable and output descriptions

Observed in `variables.tf`, `outputs.tf`.

- Every `variable` and `output` has a `description`.
- Descriptions are full sentences ending in a period.
- Other inputs are referenced as `var.<name>` or in backticks: "Required if `azs` is not provided."
- Optional inputs may start with `(Optional)`. Use the prefix only if the file already uses it.
- Constraints and incompatibilities are stated in the description: "Incompatible with `az_count`".
- `validation` blocks carry an `error_message` that includes an example valid value.
- Outputs that return a map or object use a heredoc description with an `Example:` block showing the shape of the returned value.
- Attribute order inside a variable block is not fixed in the reference (`type` first in some, `description` first in others). When adding a description, keep the block's existing order and insert `description` after `type` when `type` is first, otherwise as the first attribute.

## Inline code comments

Observed in `main.tf`.

- Banner separators above each resource group: `# ---------- PUBLIC SUBNET CONFIGURATION ----------` (uppercase, ten dashes each side).
- Short lowercase notes under the banner for conditions: `# NAT gateways (if configured)`.
- Behaviour notes for modes: `# When mode = "existing", EIPs are not created; allocation_ids are used directly.`
- Linter suppressions on their own line: `#tfsec:ignore:aws-ec2-require-vpc-flow-logs-for-all-vpcs`.

## Upgrade guides

Observed in `docs/UPGRADE-GUIDE-4.0.md`, `docs/UPGRADE-GUIDE-3.0.md`.

- File name `docs/UPGRADE-GUIDE-<major>.0.md`.
- Title `# Upgrade from version <prev> to version <major>`.
- Sections: one paragraph on why, `## Preparation for upgrade` (numbered, starts with a state backup), `## Upgrade procedure` with `### Overview` (numbered list ending in "Verify no unintended changes via `terraform plan`") then one `###` per resource or variable group with the exact `terraform state` commands.
- Numbered lists use `1.` for every item.
- The root `.header.md` carries an italic note linking to the latest guide only.

## Commit messages

Conventional commits are used: `feat:`, `fix:`, `docs:`. Observed in `git log` (`fix: regenerate README with terraform-docs v0.19.0 (CI version)`).
