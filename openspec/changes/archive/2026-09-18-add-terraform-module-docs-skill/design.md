# Design

## Context

The repository currently contains only a LICENSE and the OpenSpec scaffold. There is no skill layout yet, so this change sets the convention. The reference module `arminhs/terraform-aws-vpc` uses the aws-ia pattern: prose in `.header.md`, `README.md` fully generated by terraform-docs v0.19.0 in replace mode, a CI job that fails when the committed README differs from a fresh run, per-example `.header.md` files, banner comments in `main.tf`, and `docs/UPGRADE-GUIDE-<major>.0.md` files. Two of its examples lack a README, which is exactly the gap this skill should catch. See proposal.md for motivation.

The intended targets are modules with no documentation, or with a README that is empty, minimal, or purely terraform-docs output. That makes it acceptable to impose one layout rather than adapt to each module's existing style; modules with rich hand-written READMEs are detected and left alone.

## Goals / Non-Goals

**Goals:**
- A single, self-contained skill directory that works when dropped into `.claude/skills/`.
- Audit first, write second, so the skill never clobbers hand-maintained docs.
- Output that passes the target module's own docs check on the first push.
- Keep `SKILL.md` short and push detail into reference files that are read only when needed.

**Non-Goals:**
- Generating Terraform code, tests, or examples themselves.
- Supporting documentation generators other than terraform-docs.
- Adapting to or preserving the prose layout of modules that already have a substantial hand-written README (inject mode, inline prose). Those are reported and skipped.
- Publishing the skill to a marketplace or plugin registry.
- A generic skill authoring framework for this repository beyond the minimal README catalog.

## Decisions

**Skill location: `skills/<name>/` at the repository root.**
Matches the Anthropic skills repository layout and keeps published skills separate from the OpenSpec tooling skills that live under `.claude/skills/`. Alternative considered: placing the skill under `.claude/skills/` so it is active in this repo. Rejected because that mixes tooling with deliverables and makes the catalog ambiguous.

**Skill structure: `SKILL.md` plus `references/` and `templates/`.**
`SKILL.md` holds the workflow (audit, write headers, fill descriptions, generate, verify, report) in under roughly 150 lines. `references/conventions.md` holds the aws-ia style guide distilled from the reference module. `references/audit-checklist.md` holds the audit items. `templates/terraform-docs.yaml` and `templates/header.md` are copied into a target module when missing. Alternative considered: one large `SKILL.md`. Rejected because Claude loads the whole file on every trigger and most runs only need the workflow.

**Frontmatter: `name`, `description`, `allowed-tools`, `license`, `metadata`.**
Follows the shape of the generated OpenSpec skills already in the repo. `allowed-tools` pre-approves `Bash(terraform-docs:*)`, `Bash(terraform:*)` for `fmt` and `validate`, and read tools. Description lists the concrete user phrasings from the spec so triggering is reliable.

**Audit as the first mandatory step.**
The audit is a read-only scan implemented with shell commands in the skill (find example dirs, grep for markers, parse variable blocks without a description). It classifies each README as absent, minimal, generated, or hand-maintained. The heuristic: a README is minimal when, after removing any terraform-docs block, fewer than roughly 15 non-blank lines and no H2 headings remain; anything larger without markers is hand-maintained. Minimal and generated READMEs are replaced, with any leading title and paragraph carried into `.header.md`. Hand-maintained READMEs gate the write steps: only source descriptions are touched. Alternative considered: regenerate everything and let the user review the diff. Rejected because replace mode destroys prose that was never moved into `.header.md`.

**Version selection for terraform-docs.**
The skill greps `.github/workflows/*.yml` for a terraform-docs tag and prefers that version. If the local binary differs, it runs anyway but reports the mismatch, since table formatting changed between minor versions and the CI diff check is strict.

**Description style is inferred, not imposed.**
Before adding descriptions the skill samples existing ones in the same file to decide on the `(Optional)` prefix and sentence style, so additions blend in. The conventions reference documents the aws-ia defaults for modules with no existing descriptions.

**Catalog README is hand-maintained.**
With one skill a generator is not worth it. The spec requires the table to match the filesystem, so the tasks include checking that on each new skill. Alternative considered: a script that regenerates the table from frontmatter. Deferred until there are several skills.

## Risks / Trade-offs

- [terraform-docs output differs between versions] → Prefer the CI-pinned version and report mismatches; verify idempotence with a second run.
- [Replace mode wipes hand-written README prose] → Audit gate: no regeneration without markers unless the user confirms migration to `.header.md`.
- [Inferred variable descriptions may be wrong or vague] → Derive from name, type, default, and usage in source; mark generated descriptions in the run summary so the user reviews them.
- [Skill imposes the aws-ia layout] → Intended, since targets are undocumented or generated-only modules. The audit classification keeps richly documented modules out of the write path.
- [Minimal versus hand-maintained heuristic misclassifies a README] → The audit prints the classification and the line count before writing, so a wrong call is visible; the user can override.
- [No environment here has terraform-docs installed for verification] → The skill and its templates are validated against a copy of `terraform-aws-vpc` in the tasks; README generation is verified where the binary is available and otherwise the fallback path is exercised.

## Migration Plan

New files only. No rollout or rollback steps beyond deleting the skill directory.
